# Cadence spec — Overview: decisions, architecture, stack

_Part of the Cadence specification v0.2 (2026-09-29). Source of truth: the Claude Doc "Cadence — spec v0.2"; these files are its export, split by area. Figures referenced below live in the Doc._

## Decisions and scope

Cadence is a self-hosted workbench for the full life of Nemotron ASR fine-tunes — data, training, evaluation, export and deployment, production flywheel. Every action is an API call, and a built-in agent (Claude Code or opencode) is a first-class operator that the user watches and steers from a chat window.

In scope: the five blocks, the agent host, the API and MCP server, the real-time event model, guardrails. Out of scope: the Эра voice pipeline itself — Cadence reaches it only through the shadow tap and the Triton model repository. UI details live in the UI shell spec.

## At a glance

The Go control plane is the only owner of state; the UI, the agents and the GPU worker are all its clients.

> **Figure:** Cadence architecture · UI, control plane, agent host, GPU worker, production — see the drawing in the Claude Doc "Cadence — spec v0.2".

The agent host is an API client like the UI: it relays chat through REST and events, while the agents themselves act through MCP tools and their own git worktrees — so every agent change becomes an event that the open panels receive at once.

## Stack

A Go control plane owns state and the contract; Python does only GPU work; a small TypeScript sidecar hosts the agents, because the official ACP and agent SDKs are TypeScript-first.

| Layer | Choice | Community practice it follows |
| --- | --- | --- |
| Control plane | Go single binary with embedded SPA; PostgreSQL; content-addressed store on disk | Same shape as the earlier Cadence concept and Polygon |
| API contract | OpenAPI 3.1, spec-first; Go server stubs generated (oapi-codegen strict server); TypeScript client and TanStack Query hooks generated | One contract, generated clients, no hand-written drift |
| Jobs | River (Postgres-backed job queue for Go): priorities, retries, one training slot per card | Queue in the same database as the state it changes; no separate broker |
| Events | Transactional outbox in Postgres → in-process bus → server-sent events with `Last-Event-ID` resume | Every change and its event commit together; no lost updates |
| MCP server | Built into the control plane, Streamable HTTP transport, tools generated from OpenAPI operations with curated descriptions | Agents get the same operations as the UI |
| Agent host | TypeScript sidecar (Node or Bun) using `@agentclientprotocol/sdk`; drivers for Claude Code and opencode | ACP is JSON-RPC 2.0 over stdio with an official TypeScript SDK |
| GPU worker | Python in the NeMo Speech 26.07 NGC container (NeMo Speech 3.0); Lhotse; runs each job as a subprocess | Pinned CUDA and PyTorch for Blackwell; recipes from NVIDIA's own fine-tuning guide |
| Data processing | NeMo Speech Data Processor configs; Lhotse Shar shards on NVMe | The pipeline NVIDIA used to build Granary |
| Recipes | One git repository per project (GitHub or internal) holding SDP configs, pipelines, mix `input_cfg`, training YAML, eval-set definitions, `data.lock` and `NOTES.md`; entities pin commit SHAs | Configs are diffable files agents can edit; runs are reproducible from a SHA |
| Evaluation | NeMo cache-aware streaming inference at deployment latency; jiwer; versioned per-language normalizers | Streaming-mode, held-out evaluation, as NVIDIA's guide insists |
| Serving and export | `.nemo` → ONNX → Triton Inference Server with sequence batching; GGUF for CPU via NeMo-Speech.cpp | Cache-aware streaming is stateful; Triton sequence batching keeps state per call |
| Frontend | Vite, React, TanStack Router and Query, Dockview, shadcn on Base UI, Radix Slate, Iconoir | See the UI shell tab |
| Tracing | OpenTelemetry across UI → API → job → agent tool call | One trace answers "which agent turn started this run" |
| Storage | Mount drivers: local path, NFS or SMB path, S3-compatible object storage (MinIO), Hugging Face Hub; content-hash index; local NVMe cache with pinning | Data stays where it is; training reads from local disk, evaluation may read remotely |
| Search and help | Postgres full-text search with trigram matching, fed from the outbox; per-locale text normalisation before indexing; pgvector for embedding search in v2. Help articles are markdown bundled in the binary | Self-hosted, one database, near-real-time; the same index serves the palette, Library and the agent's search tool |
